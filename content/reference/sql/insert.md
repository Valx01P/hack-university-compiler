# Inserting Rows

`INSERT INTO table (columns) VALUES (...)` adds rows. Always name the columns, so the statement survives new columns and lets identity and default columns fill themselves.

```sql
CREATE TABLE users (
    id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  text NOT NULL,
    email text NOT NULL UNIQUE,
    score integer NOT NULL DEFAULT 0
);
```

### One row, many rows

```sql
INSERT INTO users (name, email) VALUES ('Ana', 'ana@x.io');          -- INSERT 0 1
INSERT INTO users (name, email, score) VALUES
    ('Bo', 'bo@x.io', 7),
    ('Cy', 'cy@x.io', 3);                                            -- INSERT 0 2
INSERT INTO users (name, email, score) VALUES ('Di', 'di@x.io', DEFAULT);
```

The tag `INSERT 0 2` means 2 rows went in (the `0` is a leftover, always 0).

### RETURNING: get the new id back

```sql
INSERT INTO users (name, email) VALUES ('Ed', 'ed@x.io')
RETURNING id, score;
-- 5 | 0
```

`RETURNING *` returns every column. It also works on `UPDATE` and `DELETE`.

### Insert from a SELECT

```sql
CREATE TABLE top_users (user_id integer, name text);

INSERT INTO top_users (user_id, name)
SELECT id, upper(name)
FROM users
WHERE score > 2;                                                     -- INSERT 0 2

INSERT INTO users (name, email)
SELECT 'user' || n, 'user' || n || '@x.io'
FROM generate_series(1, 3) AS n;                                     -- 3 test rows
```

### Upsert: ON CONFLICT

```sql
-- skip rows that would break a unique rule
INSERT INTO users (name, email) VALUES ('Ana 2', 'ana@x.io')
ON CONFLICT (email) DO NOTHING;                                      -- INSERT 0 0

-- or update the row that is already there
INSERT INTO users (name, email, score) VALUES ('Bo', 'bo@x.io', 10)
ON CONFLICT (email) DO UPDATE
SET score = users.score + EXCLUDED.score;                            -- Bo now 17

-- update only when something changed
INSERT INTO users (name, email) VALUES ('Cy', 'cy@x.io')
ON CONFLICT (email) DO UPDATE
SET name = EXCLUDED.name
WHERE users.name IS DISTINCT FROM EXCLUDED.name;                     -- INSERT 0 0
```

`EXCLUDED` is the row you tried to insert. `users` (the table name) is the row already stored.

### Use it in a loop: counters

```sql
CREATE TABLE word_counts (word text PRIMARY KEY, n integer NOT NULL);

INSERT INTO word_counts (word, n)
SELECT w, 1
FROM unnest(ARRAY['a', 'b', 'a']) AS w
ON CONFLICT (word) DO UPDATE SET n = word_counts.n + 1;
-- ERROR:  ON CONFLICT DO UPDATE command cannot affect row a second time
```

One statement can't hit the same key twice. Group first, then upsert:

```sql
INSERT INTO word_counts (word, n)
SELECT w, count(*)
FROM unnest(ARRAY['a', 'b', 'a']) AS w
GROUP BY w
ON CONFLICT (word) DO UPDATE SET n = word_counts.n + EXCLUDED.n;   -- INSERT 0 2
-- word_counts now holds a | 2 and b | 1
```

| Form | Does |
| --- | --- |
| `VALUES (...), (...)` | literal rows |
| `DEFAULT` | the column's default, in a `VALUES` slot |
| `DEFAULT VALUES` | a row of all defaults: `INSERT INTO t DEFAULT VALUES` |
| `SELECT ...` | rows from a query |
| `RETURNING cols` | prints the inserted rows |
| `ON CONFLICT (col) DO NOTHING` | skip duplicates |
| `ON CONFLICT (col) DO UPDATE SET ...` | upsert |
| `OVERRIDING SYSTEM VALUE` | lets you write a `GENERATED ALWAYS` id |

### Gotchas

- Strings take single quotes. `"Ana"` is a column name, so `VALUES ("Ana")` fails with `column "Ana" does not exist`.
- `ON CONFLICT (col)` needs a `UNIQUE` or `PRIMARY KEY` on exactly those columns.
- Inserting an explicit id into a `GENERATED BY DEFAULT` column does not move its counter, so a later default id can collide.
- `INSERT INTO t VALUES (...)` without a column list depends on column order and breaks when the table changes.
